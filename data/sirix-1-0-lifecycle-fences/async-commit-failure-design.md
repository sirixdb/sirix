# Async commit failure and recovery

Decision: “A, but with a clear design of course. Why does the cleanup for instance fail? It should simply be a truncation once a \".commit\" file is in the resource”.

R4 is a shared completion-boundary defect. The implemented slot, failure and teardown contracts are owned by [the async commit design](../../docs/ASYNC_COMMIT_DESIGN.md#failure-and-teardown-ownership).

R5 is an ownership/recovery abstraction defect: closed means unusable, not recovered. After fencing workers, bound and unbound writers release independent in-memory ownership even when cleanup fails. Recovery is exclusively the existing marker-driven admission barrier. The same contract covers public clean close, explicit session abort, failed rollback and both node/page writer admissions, for XML and JSON. Public dirty close remains refused.

Truncation repairs persisted state. Successor construction, task submission, catalogue serialization, data/beacon writes, cache invalidation, listener/reader/log/backend close and marker I/O can independently fail; none warrants a second disk-repair algorithm. The admission contract and marker-creation failure handling are owned by [marker recovery](../../docs/operations.md#marker-recovery).

For the final teardown boundary, see [ResourceSession.close()](../../bundles/sirix-core/src/main/java/io/sirix/api/ResourceSession.java) and the [async ownership design](../../docs/ASYNC_COMMIT_DESIGN.md#failure-and-teardown-ownership). These supersede the initial proposed cleanup order: scheduler shutdown follows node cleanup; external transaction close fences termination before write-permit release outside the node lock. Scheduler-initiated close instead returns through the safe callback epilogue, as specified in R6 below.

Successful hardening work and record/page loops retain their ordering. Recovery adds I/O only when the marker/guard is present. Failure-only marker retention and slot completion share boundaries; no retries or second disk recovery subsystem is added.

## Executable specification / independent oracles

- Construction or submission plus hardening failure: first injected error identity, suppressed hardening error, async permit count exactly one, repeated await retains cause; session abort frees the shared permit and scheduler in XML/JSON.
- Failed prewrite teardown: marker exists despite terminal writer state; a second user opens only after truncate/catalogue/cache recovery, sees the recorded durable value, commits a new value and reads it back. Bound/unbound owners obey the same barrier.
- Recovery fault at truncate/catalogue/cache stage: no reader construction or writer returned, marker-naming error and permit returned; clearing the fault permits recovery. Marker creation failure cannot produce a clean admission after the first session closes.
- Durable boundary: pre-beacon failure keeps revision 1; post-beacon cleanup failure keeps revision 2. An appended garbage tail is removed at admission, not teardown. Sibling resource caches remain usable.
- Existing real paused-worker tests cover R2/R3 and public dirty close; lifecycle iterator/axis tests remain unchanged.

This review phase runs one focused core verification round after all edits. Scoped PIT, work budgets, compiled-shape comparison and broader validation belong to the outer executor; no historical result is claimed for this revision.

Rollback ownership checks precede failure recovery: calling rollback on a closed node must reject without creating a marker or changing a successor writer's admission state. A failed rollback must reject mutations/commit until a successful rollback reconstructs the epoch. Existing rollback-only state provides that guard. The bound prewrite fault test uses the production KEEP_OPEN_ASYNC_FLUSH mode, whose epochs append to the reclaimable data tail rather than the default spill file.

## R6: scheduler-initiated teardown

A termination fence may only be performed by a thread outside the executor being fenced. Both XML and JSON timed transactions may close themselves, or their session, from a public post-commit hook. Such close completes node cleanup, publishes CLOSED, shuts down scheduling and releases admission exactly once without waiting for its own thread. Once a hook closes the transaction, neither synchronous nor asynchronous publication dispatches another hook. The timed callback then only returns through the lock-release/executor epilogue; it must never revisit readers, writers or epoch state.

Remember the scheduler worker's identity at thread creation, not by thread name. External close still waits for termination, including a repeated close after scheduler-initiated teardown. Do not hold the transaction monitor during that fence or while waiting for a timed transaction's lock: a scheduler hook can need to enter close concurrently. Timed cleanup uses its existing transaction lock; untimed cleanup remains serialized by its monitor. The existing admission-release guard becomes atomic so independent closers cannot release twice.

Regressions use real timed XML/JSON transactions, latches and a queued external closer. They prove transaction-close and session-close hooks return, another user reads the committed value and writes while the old hook is paused, no later hook runs on closed state, and external close returns only with the executor terminated. Bounded completion waits are deadlock guards, not performance assertions. Successful ordinary hooks retain their order; count-based asynchronous publication follows the same close-stops-hooks rule.

## R7/R8: complete teardown lock ordering

Confirmed: session close held the session monitor while waiting for a transaction lock, and public rollback held the transaction monitor while waiting for that lock. A timed callback already owns the transaction lock and can call either close entry point; those opposite edges create cycles. An open check made before acquiring that lock is stale once the callback closes the transaction.

Invariant R7: no session or transaction monitor may be retained while waiting for a timed transaction lock or scheduler termination. Invariant R8: rollback validates open state under the ownership lock, before maintenance and outside the failure catch that marks recovery. These hold for public rollback, transaction close, session rollback/abort, repeated/concurrent close, both formats and FILE_CHANNEL/IN_MEMORY.

Ordering: session inventory and close-attempt accounting use a short session-monitor section; transaction rollback/abort and scheduler fences run outside it. Timed node cleanup/rollback uses only the existing transaction lock. Untimed node cleanup/rollback remains serialized by the transaction monitor, with no timed scheduler to wait on. Internal abort owns rollback plus cleanup as one atomic node operation so competing session closers never issue a stale public rollback between node transitions. Scheduler self-close retains R6's safe epilogue; external node abort still fences after dropping its ownership lock/monitor.

After node owners have been processed, the session monitor serializes the existing independent-reader/cache/pool/storage/store cleanup and final state transition. An already completed concurrent session close skips that tail; any legitimate failure already retained is still reported. The short close-attempt count preserves the writer/user-session admission serialization formerly supplied by the whole-method monitor, including overlapping failed attempts; it is not a retry policy or disk-recovery mechanism. Node callbacks may register replacement readers during rollback, which the tail still collects. Unfinished workers retain dependent storage and remain retryable.

The hidden shared-session reference-count monitor is reached only by final registration release, after node shutdown/fencing; it never surrounds the user-session transaction phase. Store/database registration monitors likewise occur in that final phase. No transaction lock or scheduler wait may be moved into those monitor sections.

Executable matrix: timed XML/JSON callbacks calling transaction.close or session.close; external transaction.close, session.close or rollback queued behind the callback; FILE_CHANNEL and IN_MEMORY. Latches prove the external caller is queued before callback teardown. The callback must return, release admission once, skip later hooks, and leave no marker; file-backed checks read committed value 1, commit value 3 and read it back, while RAM checks empty-bootstrap admission plus mutation/rollback. Stale rollback must reject without poisoning marker recovery, which is independently demonstrated by successful IN_MEMORY write admission. An external session close in progress must reject a new writer on that same session while the callback remains paused.

RAM verification adjustment: the initial run passed 154/166 cases, including every file-backed interleaving; the 12 new RAM cases failed before entering the queued sequence because the fixture assumed persisted value revisions. RAM does not implement the file-backed revision/bootstrap protocol. Its root reference also used key -1 although the published root was stored under an allocated key, so the lifecycle root reader returned null. The additional invariant is that a published root's embedded page and storage key resolve the same object. Correct that reference at the RAM backend boundary; close, rollback and any keyed root consumer then agree without adding a second root-reading path. Keep unsupported truncation unchanged.

The RAM cases use an empty-bootstrap lifecycle oracle: timed publication of the empty resource, no marker or recovery guard, another user's actual mutation followed by successful rollback, and clean writer admission after the stale rollback finishes. File-backed cases retain the committed-value 1/3 durability checks. A direct RAM writer/read test publishes two different roots and checks that the returned reference reads the latest one by its key. This does not claim repair of unrelated RAM revision persistence or page-sharing behavior.

## R9: owner registration through admission release

Confirmed ownership flaw: the bound reader's close callback removed the node owner before scheduler fencing and write-permit release. A concurrent session close could then publish the session closed, causing the first closer's release callback to fail before its finally block; the node's atomic release guard had already been consumed.

Invariant: a registered node writer remains registered through reader cleanup and scheduler fencing until its shared write permit is actually released. This applies to ordinary public close, explicit session abort, both competing session closes, repeated close, final registry cleanup, and XML/JSON timed and untimed transactions. CLOSED describes unusable payloads, not completed admission ownership.

Ordering: reader callbacks retire only read-only registrations. After node cleanup and the existing external scheduler fence (or R6's safe self-close epilogue), the session monitor serializes node-owner removal and permit release as one short operation, with release in finally. The registry itself supplies exactly-once ownership; remove the separate pre-consumed atomic node guard. A later callback for an absent owner is a no-op, including after session closure. Session finalization preserves every internal node registration still present and cannot publish closed while any remains. No lock or executor wait occurs inside that release operation. Existing R7/R8 ordering and marker recovery remain unchanged; IN_MEMORY marker-policy changes are deferred.

Derived regression: pause the first closer at the real scheduler termination-check boundary after reader cleanup, with a second user holding resource lifetime. Assert the closed node remains registered and admission is held. Run another session close, which must discharge that same registered obligation before publishing closed. Resume the first closer and repeat close; admission must remain exactly one, maps empty, callbacks complete, and the second user must read the durable value, write and close. Cover XML/JSON, public transaction close versus session abort, timed/untimed schedulers, and a writer teardown failure. Existing timed hook tests retain the reentrant scheduler coverage; existing injected cleanup tests retain primary/suppressed-error checks.

Final registry cleanup retains internal node owners from the current registry, while preserving the previous retirement of ordinary read registrations and completed interface-only owners, including registrations created by cleanup callbacks. The initial node map copy is consequently unnecessary; the identity snapshot of transactions still drives cleanup outside the monitor.

## TXN admission ordering (R10)

TXN-ADMIT-1: Neither node-writer nor unbound page-writer admission waits for the resource write permit while retaining the session monitor. Validate parameters and current session state under a short monitor section, acquire admission without that monitor, then revalidate open/closing state under the monitor before constructing or registering any writer. Release the acquired permit in finally if revalidation or construction fails. The existing marker recovery barrier remains inside exclusive admission and precedes reader construction.

TXN-ADMIT-2: Owner removal and permit release remain atomic under the session monitor; node cleanup and scheduler fences never wait under that monitor. Thus admission uses permit acquisition followed by a short session-monitor section, while finalization only releases the permit and never waits for it under a monitor. Both node and page admission, ordinary node close, unbound page close, concurrent session close and construction failure obey this order.

Derived regression: queue each admission kind on an existing node or page owner, observe the semaphore queue, then close the old owner from another thread. Both calls must complete, admission must return a usable writer, and final close must restore exactly one permit. XML and JSON are covered; a session closing while admission is queued must make the eventual admitted attempt reject without constructing a writer or leaking admission. Callback dispatch contract clarification is pending because KEEP_OPEN holds this lifetime permit and PreCommitHook precedes publication; no change to either contract is inferred here.
