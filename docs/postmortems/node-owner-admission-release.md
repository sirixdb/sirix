# Bug: reader cleanup retired the writer's admission owner

- Fix / issue: lifecycle audit V05/V06, review R9; continuation of [R7/R8](scheduler-close-lock-ordering.md).
- Symptom: concurrent session closes, or public transaction close racing session close, could permanently retain the shared writer permit even though the node payload and session reported closed.
- Trigger: another user keeps the resource alive; pause the first closer after node reader cleanup and before write-permit release, then close the same session from another thread.
- Root cause: the bound node reader used the read-only deregistration callback, which removed both node and page-writer mappings before node-level scheduler fencing and admission release. The second closer saw no owner and published session closure. The first closer consumed its independent atomic release guard before a session callback that rejected the closed session outside its release finally. Registration, terminal payload state and admission ownership had different lifetimes.
- Why tests missed it: the timed callback matrix queued the external closer before callback teardown. It never took a fresh inventory after reader cleanup, and did not check ownership while another writer held the same shared semaphore.
- Regression test: `NodeTransactionAbortLifecycleTest.lateConcurrentCloseRetainsOwnerUntilPermitRelease` covers 16 XML/JSON, timed/untimed, ordinary-close/session-abort and writer-failure combinations. A delegating scheduler double pauses only the first closer at the actual termination-check boundary, after real cleanup and termination. The second close must observe the owner, discharge its permit and empty the registry before session closure. The first closer then resumes while the next writer owns admission; repeated old closes must leave its permit held. Durable value 0, a new commit of value 3 and a subsequent read provide independent storage oracles. Injected terminal writer failure remains the identical primary error; existing failure suites retain suppression checks. The old code removes the registration before the first latch, so it fails the owner assertion. No pre-fix execution is claimed.
- Lesson: retain admission owners until actual release, and use the registry itself for exactly-once discharge; see [Lessons](../LESSONS.md).

The [governing design](../../data/sirix-1-0-lifecycle-fences/async-commit-failure-design.md#r9-owner-registration-through-admission-release) was written before tests and implementation. Reader cleanup now leaves node writers registered; the short synchronized release boundary removes that owner and releases in finally, without any transaction-lock or executor wait. Session finalization preserves remaining internal node owners. R6 self-close and R7/R8 lock ordering remain unchanged. No marker-policy or record/page-loop change is included. Fresh PIT and compiled-path evidence belong to the outer executor.

The first focused run passed all 166 existing cases; the 16 new cases failed at fixture setup because an already-terminated executor skips awaitTermination. The latch now gates the successful isTerminated observation at the same real fence boundary, including that fast path. Assertions and production code are unchanged by this fixture correction.
