# Bug: commit callbacks inherited enclosing execution ownership

- Fix / issue: lifecycle audit V05/V06, R11 and review-1; clarified captain option A supersedes the earlier R6 reentrant-close behavior.
- Symptom: a count-triggered post-hook could close its node/session while a scheduler task waited for the setter's outer lock, then join that scheduler forever. Writer admission remained held. Moving only an inner runLocked block did not release the setter's acquisition.
- Trigger: KEEP_OPEN with count 1 and a timer; pause the count commit while a scheduler task queues, then invoke commit/rollback/abort/close from a hook. Foreground, scheduler and async publication had separate dispatch sites. JSON additionally retained a monitor/outer runLocked wrapper around rollback.
- Root cause: callback execution had no shared lifecycle context or outermost execution/borrow boundary. Scheduler-thread exceptions covered one caller identity, not nested foreground ownership, async observers or captured session references.
- Why tests missed it: previous tests explicitly accepted reentrant hook close, exercised only scheduler-thread closure, or observed ownership after callback teardown. They did not prove immediate rejection across all hook/listener types or post-delivery outside the setter's outer T and scheduled Runnable.
- Regression test: `callbacksRejectLifecycleBeforeLockingAndRunAfterExecution` covers XML/JSON explicit, mixed count+timer, timer and async paths. The mixed case queues the real scheduler behind a latched pre-hook before completing the foreground setter. Every pre/post/listener callback attempts every guarded lifecycle entry point and requires the callback-rule exception; post/listener work observes T released and the scheduled task ended. `externalCloseFencesCallbackPayloadOwnership` holds a real callback while an external close waits on the execution condition, then proves payload usability, shutdown, exact admission release and another user's durable value 1/new commit 3. Its async case delays hardening until foreground mutation has returned, respecting untimed single-thread row ownership. `enclosingExecutionCannotEnterATerminationWait` covers arbitrary runLocked close. `TransactionExecutionLockTest` covers nested unlock, scheduled Runnable completion, and failure/phase restoration with later notifications attempted. Existing ordinary hooks, paired hardening/construction faults, late concurrent-close and queued-admission matrices remain. No pre-fix execution is claimed.
- Lesson: establish one callback context and the actual outermost execution boundary, reject lifecycle reentrancy before locks, and fence callback borrows before retiring payloads; see [Lessons](../LESSONS.md).

The [TXN requirements](../../data/sirix-1-0-lifecycle-fences/async-commit-failure-design.md#txn-callback-contract-r11--review-1-clarified) were written before implementation. P remains owned; pre-hook veto timing is unchanged. A callback-aware execution lock centralizes outermost release and scheduler completion instead of changing every mutator or adding another scheduler-thread exception. It queues only configured notifications, introduces no per-row allocation, and leaves untimed no-lock row paths intact. Timed execution boundary checks necessarily change compiled locking work: fresh outer compiled/work-budget evidence is required and no historical unchanged-shape claim is made. No budget bound is widened.

Post-publication notification faults are isolated, accumulated with suppression and logged after restoring ownership. This explicit delivery change prevents a callback error from replacing an already-unwinding mutation/cleanup error; pre-publication hook failures still propagate and veto. Successful async publication is observed only after root cleanup and async slot release. The existing pending-root regression now asserts that deferred timing while retaining its independent durable-root, first-failure and recovery-value oracles.

The first focused invocation compiled production but stopped at test compilation on an ambiguous JUnit method reference; the fixture now uses an explicit void lambda. Final tracing also covered publication before registry insertion: a timed task can start during construction. A cold execution-owner context now routes foreground publication to its execution boundary even without a registry entry; background hardening uses the owner registration retained through async-slot release. `publicationBeforeOwnerRegistrationStillUsesTheExecutionBoundary` removes the registration during a real commit, requires every actual listener to see T released and the callback guard active, restores registration, and proves exact release plus durable value 1. It models that window without timing assumptions or source inspection. No publication or revision value is deduplicated.

Final tracing extended the invariant to cold lineage operations and final session notifications. `untimedRevertCompletesNotificationDelivery` verifies delivery after the rebuilt view is ready; `finalSessionNotificationsStillRejectLifecycleBeforeClosedChecks` verifies callback rejection even after final session publication. `lineageChangesFenceHardeningBeforeWriterRecovery` covers eight JSON/XML revert/truncate success/failure interleavings: commands must wait for hardening, retain the original failure and leave admission reusable with independently checked durable values. Revert/truncate now use the existing hardening fence. Redundant foreground dispatch and obsolete callback-cancellation handling were removed; one execution boundary owns delivery.
