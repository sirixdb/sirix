# Bug: Conditional-write specification boundary conflicts

- Fix / issue: Review findings R1–R8 on `fm/sirix-spec-revision-token`; specification-only corrections to [TXN-311](../../spec/TXN-transactions-durability.md#txn-311--conditional-write-preconditions), VER-206, FMT-209, CONF-102/103, JAPI-111 and REST-204/205/210/211/212.
- Symptom: The draft rejects valid child-position and disjoint boundary inserts, makes verdicts depend on hashing, can repeat tokens after database recreation or restore, leaves cross-resource query mutations unguarded, requires response tokens where no head exists, misses XML attribute/namespace membership changes, and adds an unapproved native/SDK release obligation.
- Trigger: The worked review cases below exercise the public contract; no conditional-write implementation exists yet.
- Root cause: Context identity, semantic modification, resource incarnation, actual mutation scope and response identity were defined differently by their producers and consumers. R1 is a local predicate error; R2–R6 expose shared contract-boundary gaps. The correction removes the non-empty parent-stamp fallback and database allocator, defines semantic stamps once in VER-206, and makes TXN-311/FMT-209/REST-212 the shared authorities for their consumers. R7 exposes an incomplete XML semantic-field inventory: attribute and namespace membership are stored separately from child/sibling links, so the surviving owner needs a stamp when a member disappears. R8 is a release-scope error: shared implementation semantics do not require simultaneous native/SDK exposure.
- Why tests missed it: All new conditional-write suites are explicitly planned. Existing hash-based implementation tests do not exercise the proposed token contract. Byte-change oracles would incorrectly treat derived hash/count bookkeeping as semantic edits. The revised semantic oracle also omitted non-root XML membership insertion/removal and retained attribute/namespace edits; a child-only head scan cannot observe a deleted non-child record.
- Regression test: Documentation acceptance is a manual before/after trace of the cases below, plus a focused audit of links, stable requirement IDs, metadata, traceability and unchanged statuses. Planned executable regression suites are named in the last column; they must run against the eventual public Java/HTTP/storage interfaces and assert persisted state, verdicts and errors, rather than inspect prose. No runtime or mutation-testing pass is claimed: this fix changes no executable logic.
- Lesson: [Review shared contracts across lifecycle and consumers](../LESSONS.md).

| Finding | Independent contract and minimal witness | Before correction | Required result after correction / planned regression |
|---|---|---|---|
| R1 | An unchanged first/last-child insertion point is valid; `A = P`, while `parent(P) != P`. | The unconditional anchor-parent comparison rejects it. | Skip the anchor-parent comparison and anchor stamp when `A = P`; check the occupied neighbour or empty-container stamp. Repeat both child modes and both sibling modes through Java and REST. `ConditionalWritePreconditionConformance`, `JavaConditionalWriteConformance`, `RestConditionalTokenPreconditionConformance`. |
| R2 | At revision R, `P = [a,b,c]`; insert after c while another writer prepends x before a. The insertion boundary is unchanged. Mirror this for insertion before a and a concurrent append after c. | Empty-neighbour fallback checks the newly stamped P and rejects both disjoint edits. | Accept both, using c or a and its unchanged empty-side link. First/last-child forms use their occupied neighbour. Empty-container transitions reject via P; changes to either context record's value/name/links or XML attribute/namespace membership, including its opposite-side link, still reject. The same TXN/Java/REST suites cover each direction. |
| R3 | Change a scalar descendant of container anchor A, leaving A's value/name/links unchanged; then insert beside A using the earlier token. Hash configuration cannot change the verdict. | ROLLING changes A's stored hash and therefore its stamp; NONE does not. | Derived hash/count-only changes preserve both stamp fields, and both modes accept the same insertion. Real value/name/link edits still stamp and conflict. `LastModifiedRevisionStampingConformance` uses an independent tree model. |
| R4 | Keep an old token, delete/recreate the database or restore an older backup, then reach the same revision number. Resource identity must survive allocator loss. | The database-local counter restarts or rewinds, reproducing the old token deterministically. | Fresh independent secure 64-bit draws at creation, truncate, replacement and restore; any particular old id recurs with probability 2^-64. Controlled distinct draws demonstrate stale-token rejection, while zero/high-bit ids round-trip through the 16-digit string grammar. Ordinary reopen and settings rewrite preserve identity; truncate publishes it before removal. `ConditionalWriteMetadataFormatConformance`. |
| R5 | A conditional query addressed to A explicitly mutates B; an unconditional query addressed to A mutates strict B. | Only the path resource has a defined precondition check. | Return 409 naming B for the conditional query and 428 for the unconditional strict-resource query, through every route and indirect mutation boundary, with no request effects. Include A-then-B and B-then-A, both header forms, database-wide 400, and an accepted same-resource control. `RestPreconditionScopeConformance`. |
| R6 | Successfully delete a resource/database or mutate multiple resources. There is no single newly published surviving head. | A universal successful-response ETag obligation has no value to return. | No ETag for those successes; one newly published surviving head returns its token. Failure responses return a token only for one identified existing resource head. Include node deletion with a surviving resource as a positive control. `RestConditionalTokenETagConformance`, `RestPreconditionFailureResponseConformance`. |
| R7 | Read non-root XML element E at R, remove its attribute at R+1, then conditionally replace E using R; repeat with namespace removal and with insertion. | The deleted member is absent from the head scan, and the surviving owner's membership lists are outside the enumerated stamped fields, so stale replacement can undo the deletion. | Membership changes stamp E, making each stale subtree replacement fail. Scan attribute/namespace records owned by every included element so retained-record value/name edits also conflict. Cover XML insertion-context membership changes, both hash modes, unchanged subtrees and disjoint edits; hash/count-only bookkeeping remains excluded. `LastModifiedRevisionStampingConformance`, `ConditionalWritePreconditionConformance`, `JavaConditionalWriteConformance`, `RestConditionalTokenPreconditionConformance` (planned). |
| R8 | The accepted 1.0 scope requires REST tokens and a shared Java core check; native/SDK exposure is deferred. | JAPI-111 makes every binding mandatory and the native open item requires header/manifest/check changes before freeze. | REST still requires the Java core check; native/SDK conditional-write exposure is an open future capability outside the native release requirements. Documentation acceptance compares the obligation and scope against the recorded decision; existing adopted native requirements remain unchanged. |
