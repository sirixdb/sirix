# Bug: async hardening failure confused ownership with recovery

- Fix / issue: lifecycle audit V05/V06, review R2–R5; design in `data/sirix-1-0-lifecycle-fences/async-commit-failure-design.md`.
- Symptom: a construction plus hardening error could strand the async permit forever; a terminal writer could instead release admission and delete the marker despite incomplete cleanup, exposing stale offsets.
- Trigger: fail successor construction or submission and inline hardening together; alternatively abandon prewrites and fail cleanup before handing off to another user session.
- Root cause: only the background route paired hardening failure retention with slot release. Node teardown used a reader/writer terminal flag as proof both of completed node ownership and safe disk reuse. Marker deletion in ordinary close erased the independent recovery obligation. Reader guard failure could also skip node-reader finalization. The first focused run exposed a path-only guard surviving database recreation; persisted identity and explicit deletion now delimit its lifetime.
- Why tests missed it: successor-construction tests hardened successfully; terminal-hardening tests constructed successfully. Clean close tests did not compose failures with warm caches, a dirty successor, a second session or marker creation failure.
- Regression tests: `NodeTransactionAbortLifecycleTest` covers XML/JSON construction/submission double failures, repeated original-cause waits, pre/post-beacon boundaries, bound/unbound cleanup failures, marker failure across session close, recovery-stage failure/retry and node-reader guard failure. `AsyncFlushFailurePathTest.unboundCloseBlocksSuccessorUntilAbortedTrieTailIsSafeToReuse` publishes real prewrites and checks cache eviction at admission, preserving a sibling resource's cache. Existing paused-worker cases cover R2/R3 and public dirty-close protection. Independent oracles are injected first-cause identity, exactly one permit, worker termination, recorded durable values, removal of appended garbage and resource-specific cache identity.
- Verification: focused results are recorded in `docs/lifecycle-fence-review.md`. No before-fix execution or mutation result is claimed for the newly added cases; the reported construction/hardening sequence statically reaches the missing release in the submitted code. Outer validation owns mutation, work-budget and compiled-shape evidence.
- Lesson: separate fenced in-memory ownership from marker-driven disk recovery, and derive a cross-product fault matrix for every owner-transfer route; see [Lessons](../LESSONS.md).
