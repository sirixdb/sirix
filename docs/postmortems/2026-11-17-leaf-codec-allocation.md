# Bug: Temporary objects in cold HOT leaf codec paths

- Fix / issue: S1 kind-12 leaf payload codec, found before commit by the explicit allocation audit.
- Symptom: On the 32-entry fixture, encoded projection copies allocated 344–384 extra heap bytes per page; uncached selection allocated 24 extra bytes; repeated-value encoder selection allocated 80 extra bytes. Raw/encoded cold full materialization and warm lookup alone had hidden these other paths.
- Trigger: Repeated raw/encoded copies, selective reads and writes with zero-filled or repeated nonzero 128-byte values, after scratch initialization, in a clean GraalVM 25 test fork.
- Root cause: The projection factory allocated an owned compressed input array before expansion allocated the retained raw array. Expansion and uncached selection also constructed parsing cursors per page. JFR then attributed the complete writer's 80 B/page to two 40-byte `NativeMemorySegmentImpl` objects from `FFILz4Compressor.compressSegmentRange`'s input/output `asSlice` calls. Moving the views into a helper passed the mixed-operation unit gate but still depended on escape analysis in the larger caller. The writer now borrows separate reusable buffers and passes base segments plus primitive lengths, eliminating both view constructions. JFR/GC verified that the writer's integer-sized allocation excess disappeared. A separate 40-byte full-read difference was traced to the existing `FrameSlotAllocator.allocate` slice/reinterpret path, present on unchanged main. Later uninstrumented selector forks also exposed two remaining LZ4 read-side views (80 B/page), which ordinary JFR sometimes optimized away. Disabling Graal partial escape analysis reproduced the excess on both uncached selection and full materialization. The range call now passes original owning segments and primitive offsets to a native adapter that invokes the same LZ4 function. This removes the views without converting owners into unchecked integer addresses or weakening allocation-era lifetimes. The content-addressed library loader is shared with LZ77; an older library without the adapter uses the existing safe Java LZ4 decoder.
- Why tests missed it: Existing correctness tests asserted lifetime and bytes, and the first GC benchmark measured full leaf materialization and warm lookup. It did not cover image factories, the uncached selector, or the encoder bake-off.
- Regression test: `HOTLeafCodecAllocationTest.encodedPathsAddNoAllocation`, run in the clean `:sirix-core:dictionaryReadViewAllocationTest` fork, compares every encoded arm with its raw baseline. The baseline failed for both content patterns; the 12-path unit gate passes with exactly equal raw/encoded totals. The standing independent gate requires five fresh forks per arm and every encoded fork within 1 B/page of the unchanged-main maximum. EA-off allocation-site comparison covers both content patterns and both selection/full materialization, preventing an occasionally successful escape analysis from concealing temporary views. `HOTLeafPayloadCodecTest.projectionScratchRejectsEveryShortFrameAndDoesNotAliasRetainedImages` pins logical bounds and ownership when the new scratch is reused. `HOTLeafCodecAllocationBenchmark` profiles both arms with JMH's GC profiler.
- Lesson: [Measure allocation at each cold entry point](../LESSONS.md#measure-allocation-at-each-cold-entry-point), including codec selection and image expansion. Owned output allocations already required by the raw API must be distinguished from avoidable codec intermediates.
