# Bug: session close and rollback inverted the scheduler lock order

Historical round: the callback behavior/evidence below predates the clarified contract in [commit callback ownership](commit-callback-reentrancy.md). Callback lifecycle reentrancy is now rejected; KEEP_OPEN admission and pre-hook timing are preserved. Historical passing counts do not validate the new dispatch boundary.

- Fix / issue: lifecycle audit V05/V06, review R7/R8; continuation of [R6](scheduler-close-self-join.md).
- Symptom: an external session close or rollback queued behind a timed hook could deadlock the hook's teardown. A stale rollback could instead create a recovery marker after the transaction was already closed; IN_MEMORY then refused every subsequent writer because it cannot truncate.
- Trigger: pause a real timed XML/JSON post-commit hook while it owns the transaction lock; queue external session close or rollback, then let the hook close its transaction or session.
- Root cause: only external transaction close had lost its monitor-before-lock edge. Session close still held its monitor across node teardown, rollback still held the transaction monitor before acquiring its lock, and rollback's open check preceded that wait. Public rollback and explicit abort were separate transitions, allowing another closer to retire the node in between. These were ownership-boundary flaws, not isolated lock calls.
- Why tests missed it: R6 exercised external transaction close only and only FILE_CHANNEL. It did not queue external session close/rollback or use RAM as the admission oracle for an incorrectly created marker.
- Regression test: `NodeTransactionAbortLifecycleTest.timedPostCommitCloseReleasesAdmissionWithoutJoiningItself` now covers 24 combinations of format, backend, callback close action and external action. Latches and the transaction lock's queued-thread observation establish ordering; bounded waits guard against deadlock. Assertions cover closed state, no later hooks, no marker, exactly one permit, external close fencing, same-session writer exclusion during close, and another user's file-backed durable reads/writes or RAM mutation/rollback. IN_MEMORY admission independently proves no hidden recovery guard remains. Existing cleanup tests retain rollback/close failure ordering and unfinished-owner retry behavior. No pre-fix execution is claimed because the known lock cycles strand non-daemon scheduler workers; the before-fix sequence is statically established.
- Lesson: map the complete caller lock graph, move all callback-dependent waits out of session/transaction monitors, and validate state under the lock that owns its transition before entering recovery handling; see [Lessons](../LESSONS.md).

The governing [design](../../data/sirix-1-0-lifecycle-fences/async-commit-failure-design.md#r7r8-complete-teardown-lock-ordering) records ordering and the admission invariant. The close-attempt count preserves prior serialized writer admission while node shutdown runs outside the session monitor; it adds no retry or disk-repair protocol. Existing maintenance readers remain allowed to finish during this phase.

Exploration found a second boundary defect in the new RAM coverage: the published root reference held the right embedded page but named key -1, which was not its allocated storage key. Generic keyed reads in writer rollback/close therefore returned null. Correcting that key at `RAMAccess.readUberPageReference` covers every consumer without a separate recovery path. `RAMStorageTruncateToTest.publishedRootReferenceReadsTheLatestRootByItsStorageKey` guards the contract with two distinct published objects. The RAM concurrency fixture uses an empty-bootstrap lifecycle oracle because repairing RAM's unrelated file-style revision/bootstrap semantics is outside this lifecycle fix; file-backed durability assertions remain intact. The initial focused run had 154 passes and 12 fixture failures before reaching the RAM interleaving.

Final focused verification: 168 cases passed with zero failures/errors/skips, including all 24 interleavings and both RAM reference/capability checks. See [per-class evidence](../../data/sirix-1-0-lifecycle-fences/lock-order-verification.json). The intermediate retry caught a fixture-only compilation error (RAMStorage is not AutoCloseable), corrected before the final pass. No production/test edits followed that pass. Fresh mutation and compiled-path validation remain pending with the outer executor.
