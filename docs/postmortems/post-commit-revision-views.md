# Bug: async hooks shared the lock-free writer cursor

- Fix / issue: lifecycle audit R15; retained R11/review-1 and R13 contracts.
- Symptom: a post-hook navigating from numeric A to B could redirect a count-only JSON setter to B, silently changing the wrong node.
- Trigger: KEEP_OPEN_ASYNC_COMMIT with no timer has no mutation lock. Hardening completion dispatches a hook while foreground successor mutations continue; the old callback reservation was not consulted by these operations or their no-op runLocked wrapper.
- Root cause: the hook argument had a read-only static type but was the live mutable writer object. Callback ownership tried to serialize a cursor whose supported fast path bypassed that boundary.
- Why tests missed it: earlier overlap tests completed foreground mutation before releasing hardening, then checked callbacks afterward. They proved durability overlap but never concurrent cursor navigation. A successful 220-case run of that model therefore did not establish cursor isolation.
- Regression test: `asyncPostHookNavigationCannotMoveTheCountOnlyWriterCursor` commits A=13/B=20, parks the pinned hook on B, updates intended writer A to 15 through count-only runLocked, and checks writer A=15/B=20 while the hook still sees committed A=13/B=20 at revision 3. `ordinaryPostCommitHooksContinueInOrder` checks distinct read-only objects, fresh document roots, exact revision 2 and dispatcher closure for XML/JSON. `externalCloseFencesIndependentRevisionReaders` preserves callback-reader lifetime across external teardown. The mixed count/timer, async hardening-overlap, late reader and Error matrices remain. No pre-fix executable run is claimed.
- Lesson: separate mutable cursor ownership at the API boundary instead of adding per-row locking; pin callback observations to the committed revision. See [Lessons](../LESSONS.md).

The [TXN-VIEW requirements](../../data/sirix-1-0-lifecycle-fences/async-commit-failure-design.md#revision-pinned-post-hooks-r15) preceded implementation. Each hook receives a fresh NodeReadOnlyTrx, opened/closed by the dispatcher at the captured uber-page revision. These dispatcher-owned readers are not exposed to the initial session node-close snapshot; node callback-job completion retains their lifetime until dispatch closes them. Ordinary session/shared readers keep their existing registration and late-close cleanup. Revision listeners remain revision-number notifications and must use independent read transactions rather than captured writer state.

The callback-borrow acquisition overrides and reservation thread were removed from TransactionExecutionLock. Timed mutation acquisition uses the inherited ReentrantLock path. Outermost unlock and scheduled task completion still detach and deliver notifications outside T; callback-job completion accounting is used only by dispatch and teardown. Count-only/no-lock row operations remain unchanged. Close waits with T released, then fences scheduler termination and releases admission through the existing registry. Marker recovery, dirty-close protection, first-error/suppression and async overlap are preserved.

A single bounded JMH comparison is authorized for timed mutation and nested commit/mutation lock work. It compares a separately compiled frozen a574857c implementation with the simplified implementation on the same machine through heavy.sh. It measures lock-path work, not disk commit latency or database throughput. Fresh compilation and **229 selected cases passed with zero failures/errors/skips**: core 221, query 8. See [verification and per-class results](../../data/sirix-1-0-lifecycle-fences/revision-view-verification.json). Both commands used heavy.sh and checked the updated 60 GB floor immediately before Gradle; available bytes were 97,245,499,392 (tests) and 97,271,701,504 (JMH). No production or test edits followed the passing run; whitespace checking passed.

The one JMH comparison completed with two forks per configuration, three warmup/five measurement iterations per fork at 500 ms, one thread. Timed mutation: before **27.103 ± 0.971 ns/op**, after **26.993 ± 0.419**. Three nested acquisitions: before **102.931 ± 8.256**, after **101.001 ± 2.374**. Reported confidence intervals overlap: no measurable regression and no established speedup. These are uncontended lock-path results, not database throughput or disk-commit latency.
