# Bug: initial reader cleanup preceded callback completion

Historical review-round design: the node callback-completion fence below was superseded
by bounded database retirement before owner cleanup; see the
[database notification contract](../hooks.md). Recorded results apply to that earlier implementation.

- Fix / issue: lifecycle audit V05/V06, R16; starting head 9683e47b.
- Symptom: session close could release an ordinary reader's page guard while a started revision listener still navigated that reader.
- Trigger: a listener opens/navigates a direct or shared reader before close snapshots ownership. The identity-backed snapshot visits that reader before its node writer, so reader close runs before writer abort reaches the callback completion fence.
- Root cause: teardown treated snapshot enumeration as dependency order. R12 refreshed late readers but exempted initial readers from that late cleanup pass; R15 separated dispatcher hook cursors but ordinary callback-owned readers remained in the unordered initial set.
- Why tests missed it: the late-reader regression created ordinary readers only after the writer was already waiting at the fence, and hook-view tests used dispatcher-owned readers outside the node snapshot. Neither required an adverse initial reader-before-writer order.
- Regression test: `sessionCloseFencesCallbacksBeforeInitialReaders` covers JSON/XML, direct/shared, closer interruption and injected cache/reader close errors. It uses real readers/backend guards, replaces registry references with a delegating reader, and explicitly arranges/asserts the same identity snapshot visits that reader before its real writer. The callback navigates before close and again while close waits, then exits; the test checks node/page/guard cleanup, failure identity/suppression and exactly one permit. `refusingNodeOwnerRetainsOrdinaryReadersUntilRetry` checks an owner refusal before its fence retains real readers and later retry completes cleanup. The after-snapshot matrix remains. No pre-fix runtime reproduction is claimed.
- Lesson: snapshot ownership independently of cleanup order; establish all producer/callback fences before retiring any reader they may use, including initial and late registrations. See [Lessons](../LESSONS.md).

The [TXN-TEARDOWN requirements](../../data/sirix-1-0-lifecycle-fences/async-commit-failure-design.md#writer-fences-precede-all-ordinary-reader-retirement-r16) preceded implementation. Session close first attempts every node writer outside the session monitor. Independent page-writer cleanup still runs, including after a refusal, preserving the earlier node/page ownership retry design. An unfinished node owner retains ordinary node/page readers and their pool for retry because its callback source is still live. Once writers are fenced, one refreshed ownership set supplies all initial and late ordinary readers; the previous late-only exclusion is removed.

The benchmarked TransactionExecutionLock, per-row locking, post-hook pinned views, callback lifecycle guard, admission release and marker recovery are unchanged. This cold ordering correction does not require another benchmark. The prior JMH and 229-case runtime evidence remain historical evidence for their source; fresh focused results for R16 will be recorded separately. Scoped PIT and final compiled/work-budget proof remain with the outer executor.

The initial verification stopped at test compilation because the shared NodeReadOnlyTrx interface exposes moveTo(0), not the format-specific moveToDocumentRoot convenience. The first runtime pass completed 239 core cases: 231 passed and eight interrupted variants failed their post-close exception expectations. Their callback navigation had already succeeded under the fence. After interruption was restored, real FileChannel cleanup reported SirixIOException rooted in ClosedByInterruptException. The oracle now permits exactly that cancellation failure (or clean completion when no interruptible I/O is needed), retains the injected cache error as primary and the injected reader error in suppression order, and still requires all reader/guard cleanup, interrupt restoration and readable committed data on subsequent admission. This follows the existing interruption/cancellation contract rather than suppressing interruption or changing backend recovery. No new reentrant lifecycle deadlock was observed.

The next pass reached all lifetime, guard, interrupt and failure-order assertions, then exposed a separate backend cancellation effect in eight interrupted cases: immediate subsequent writer recovery reused a FileChannel that interruption had closed. The regression now requires that admission reject with the precise ClosedChannelException cause and restore its permit, then closes/reopens the backend and verifies committed value 1. Non-interrupted cases still require immediate writer reuse. This reports the existing cached-channel limitation rather than accepting arbitrary errors, pretending immediate reuse succeeded, or changing I/O/recovery machinery in the cold ordering fix. The in-flight callback's own navigation remains mandatory and succeeds before any cleanup I/O is allowed.

A fixture-ordering run passed all interruption/backend-reopen assertions but two cases could not construct the requested adverse snapshot: when the fixed writer identity occupied the first identity-table bucket, changing only the reader identity could never put it first. The fixture now varies delegating identities for both real owners and still requires an explicit reader-first snapshot before close starts. Setup failure cleanup also releases the callback's inspection loop. This changes no production behavior or safety assertion; it removes dependence on a lucky fixed writer hash.

Final fresh compilation and focused verification passed: **247 selected cases, zero failures/errors/skips** (core 239; query 8). See [per-class results and exact source binding](../../data/sirix-1-0-lifecycle-fences/reader-fence-verification.json); log: `build/lifecycle-reader-fence-complete.log`. The required disk check reported 96,772,993,024 bytes available, above 60 GB. No production or test edits followed the passing run; whitespace checking passed. The benchmarked lock source matches 9683e47b exactly, and no benchmark was rerun. Fresh scoped PIT and final compiled/work-budget proof remain with the outer executor. The cached-channel cancellation limitation remains explicitly reported in the evidence.
