# IndexDef, the HOT trie, and projection-directory startup

The captain is right that **IndexDef already identifies the index, and the trie already locates its persisted data**. The extra directory is a current serving representation, not information missing from IndexDef and not an inherent requirement of JSON queries. A crucial distinction: this projection trie is keyed by **row-group id and segment id**, not by the projected values such as `collection = post`.

Evidence snapshot: HEAD `165681b071dc2426742d779100b600081fbcdfa0` plus the unaccepted directory-batch candidate (storage source SHA `bb0c29796d5e61f082c6f4e264e537e47f5c961a46447c655854d90bdf3c62b7`). Investigation only; no architecture or benchmark-protocol change.

## Why the executor walks now

`lookupCovering` selects a matching definition, then `load` probes metadata slot 0 and hydrates a cached handle keyed by resource, definition and build revision. `tryBuildColumnLazyHandle` **unconditionally reads all row-group directories** before it constructs ProjectionColumnStore. It receives the definition, not the query predicate. The resulting store supports column-only batched reads without a root descent for every segment. See [ProjectionIndexCatalog.java:299](/home/johannes/.treehouse/sirix-cdde48/1/sirix/bundles/sirix-core/src/main/java/io/sirix/index/projection/ProjectionIndexCatalog.java:299), 456 and 566–665.

It already uses a range iterator: the serial directory path opens `HOTRangeCursor` over the positive row-group slot range ([storage:3022](/home/johannes/.treehouse/sirix-cdde48/1/sirix/bundles/sirix-core/src/main/java/io/sirix/index/projection/ProjectionIndexHOTStorage.java:3022)). The committed-reader path substitutes a partitioned subtree walk to overlap leaf loading/decompression, followed by capture and deterministic replay (2235–2440). Saying that Sirix does not use its trie or range cursor would be incorrect. The issue is **how much it enumerates before knowing what this query needs**.

Full directory construction is required by today's column-store constructor and serving contract, not by query semantics. Its checks reject missing/duplicate/extra descriptors, missing/undeclared segments, bad inline hashes and inconsistent physical order ([DirectoryWalk:2822](/home/johannes/.treehouse/sirix-cdde48/1/sirix/bundles/sirix-core/src/main/java/io/sirix/index/projection/ProjectionIndexHOTStorage.java:2822), 2980). A targeted/lazy alternative must preserve relevant revision, completeness, integrity and lifetime guarantees; merely skipping these checks is not a correct optimization. The generic fallback and existing point-read APIs demonstrate that this particular eager representation is not the only way to read correctly.

| Q3 | Groups that may contain commit/create rows in the three named collections, with their timestamps. |

## Follow-up: is the directory unnecessary?

**An all-columns, all-groups locator directory is unnecessary as a universal prerequisite.** It is useful for amortizing repeated queries and coalescing I/O; that does not establish that it pays for itself in this fresh-process workload. Actual consumers are ProjectionColumnStore's constructor (425), zone mirrors (1235), per-column offset collection (3100 onward), inline-byte carriers, segment integrity verification and the handle's segment-prefetch path (ProjectionIndexRegistry:1175). The duplicated work is extracting and retaining addresses already navigable through the trie, including columns this query will never read. Reconstructing this reusable state per process loses much of its intended amortization.

Measured before predicate selection: Q1 catalog lookup **3,161.4 ms** plus prefetch kick **159.7 ms**, inside a **4.195 s** query; Q4 lookup **3,182.7 ms** plus kick **126.9 ms**, inside **5.771 s**. These are one bounded diagnostic observation per query, not paired scores or exclusive capture-method time. The directory component alone was 2,900.1/2,932.6 ms. Directory construction is therefore a material startup target even when predicate pruning is weak.

Direct or lazy trie access can preserve query correctness with query-scoped readers, saved-stamp validation, descriptor/segment verification, physical-order mapping and explicit missing-data handling. The storage already has the required point/range primitives. A bounded range reader that captures only needed descriptors/columns is a plausible generic alternative; a lazy address lookup could defer unused segment locators. Neither requires an answer cache or global prepass. However, traversing/decompressing the same mixed-slot HOT leaves may remain necessary for Q1 and nearly all current Q4 groups, and independent point descents can cost more than a range walk. The exact gain is unmeasured. A replacement should distinguish its semantic correctness checks from the current eager whole-index audit, preserve the project's corruption contract, and be tested on revisions, gaps, deletes, inline/overflow data and eviction before accepting latency. **The current implementation does not justify keeping the eager directory unchanged; it supplies invariants and a baseline to beat.**

## Historical ClickBench: the same implementation?

**Yes, the exact directory-storage and catalog source files were present in the scored historical ClickBench revision.** Comparing `465f208946549e8a264598e986585942e1c8868c` with committed native baseline `165681b071dc2426742d779100b600081fbcdfa0` gives identical Git blobs: ProjectionIndexHOTStorage `c80e461e750d43a538045a5102bf60e555b82d9d`; ProjectionIndexCatalog `7b79a4782642a7d98cbaba1566f2ba550b8cc89f`. The historical storage includes `captureLeafDirectorySlots` at 2635 and the parallel-directory call at 2248; the historical catalog calls the all-directory reader at 592. The active unaccepted batching patch changes that capture loop, so it is not the historical implementation.

The historical ClickBench entry point looked up the catalog and kicked prefetch **before** per-query timing (historical ClickBenchRunMain:219–230); its query timer at 458 covered execute/serialize. The current JSONBench timer starts before `warmCatalog` (JsonBenchRunMain:309–315), and the protocol launches a new process per attempt. Thus the historical code really had this directory implementation, while the benchmark exposed/amortized its startup cost differently. The source and old command support that conclusion; they do not establish exclusive historical directory milliseconds or identical native machine code. The historical scored process was JVM/C2. No timing boundary is moved by this investigation.

## Write-maintained metadata assessment (captain 025)

**Persisting a compact directory during ordinary writes could remove a real reconstruction cost.** Descriptors, inline bytes and overflow references already persist in HOT; duplicating them blindly would add storage without proving a gain. What is missing is a directly openable, bounded, column-addressable descriptor/locator representation whose anchor can be read cheaply for this revision. Current ProjectionIndexMetadata stores schema, row-group count, build revision, set-summary capabilities and dictionary anchors (fields 152–230), **not** a per-row-group/column offset directory. Physical-order/fence chunks already persist separately (ProjectionIndexFences:29–38), so their mapping should be reused rather than reinvented. Dictionary header anchors are record keys, not segment file offsets.

| Consideration | Direct/lazy reads from existing HOT | Write-maintained directory chunks |
|---|---|---|
| Read shape | Use known physical ids, bounded ranges and requested segment kinds; retain only query-needed locators. Existing format works. | Small manifest selects descriptor/column locator chunks; fetch only selected chunks. This can avoid decoding mixed-slot HOT leaves at all. |
| Location identity | Resolve durable side-page offsets at read time; a heap PageReference or native address never becomes persistent metadata. Inline bytes still come from their owning HOT leaf. | Store durable file locations or stable logical references, explicit inline/absent forms, lengths/hashes and generation/shape evidence. A logical HOT slot id alone does not save the trie traversal. Inline payloads need a carrier or still require their original leaf. |
| Publication | Existing revision root and CoW tree already select the consistent version. | Children and affected chunks must be durable before a new revision exposes their manifest. No independently published side file or partially refreshed root. |
| Mutation | Existing put/patch/tombstone paths remain authoritative. | Patch only affected bounded chunks; preserve old revisions. Handle splits, reordered physical ids, deletes, live-empty groups and inline↔overflow transitions; unchanged segment locations can be carried forward. |
| Reopen/recovery/eviction | Reopen existing roots; saved stamps and side-map lifetime protection cover page eviction. | Reopen solely from committed anchors; incomplete/unrecognized metadata falls back safely. No serialized process pointers, cached reader leases or dependency on live HOT objects. Recovery must never pair old locators with new descriptor hashes. |
| Added cost | No write/storage duplication; repeated root descents or mixed-leaf decoding can offset capture savings. | Additional bytes roughly `8 × referenced locations + descriptor/inline carriers + chunk manifests/checksums`, before encoding and version retention. CoW chunk rewrites, validation and serialization add write cost; exact amount must be measured. One monolithic full rewrite per commit would violate the intended bounded incremental design. |

Concrete publication evidence: `HOTLeafPage.commit` (4649) commits side references before the leaf; `NodeStorageEngineWriter.commit` (3613) assigns fresh overflow offsets and rejects unresolved/pending writes. Therefore an importer cannot assume that an in-memory segment already has a durable address. Builder `finishPersist` (1216–1261) publishes slot-0 metadata after its derived chunks, within the caller's transaction. Incremental `ProjectionIndexChangeListener` tombstones groups at 2313, publishes refreshed metadata at 2418, and patches columns at 2897; `putColumnPatches` (storage:511) and row-group put/delete (698/1026) are the mutation seams a new directory must cover. Any second reference graph also needs an explicit ownership/commit-order design, not two mutable owners of the same PageReference.

**Smallest justified next experiment:** after the active batching result, test a bounded, query-scoped locator reader against the existing full-directory reader on the same committed fixture: request one column, then all columns; compare descriptors and returned bytes/offset identities, measure HOT leaves loaded/decoded, captures, allocations and time. Start at 1M under the guard, retain exact before/after attempts, then use a bounded 100M diagnostic only if it shows a useful signal. This isolates whether avoiding unused locator construction pays without changing storage format, rebuilding the corpus or moving setup outside timing. It is a proposed experiment, not an accepted optimization or a claim of speedup.

If the same HOT-leaf decompression still dominates that experiment, compact write-maintained chunks become the stronger design hypothesis. Prototype them on small new databases with commit/rollback/reopen, updates/deletes and eviction tests before any large import. Existing 100M databases must stay readable without a query-time global backfill/prepass; no destructive reimport or format migration is performed under this assessment. A new representation would require a supported version/capability and fallback policy plus measured import/storage costs. It stores access metadata only, never query answers.
