# Evidence retention: five raw archives were discarded

The derived summaries, CSVs, plots, manifests and the `docs/CLICKBENCH_RIG_*.md` write-ups in this
tree are what justify every claim the rig makes. The raw archives below were the bulk of the
evidence weight (about 44 MB of 45 MB), no script in this repository reads them, and they were
removed from the deliverable. They are **not** regenerable, so the replays that needed them are
gone, not merely relocated.

They held per-leg raw logs, telemetry, JFR recordings, `perf` CPU samples, original launch commands
and the analysis scripts that consumed them. `raw-members.json` beside the JFR archives still lists
every member and its hash, so what was inside them remains named even though the bytes are gone.

## What can no longer be replayed

- The JFR/`perf` replays documented for `jvm-diagnostic-20260908` and `placement-jit-20260908`.
  Their committed `analyze*.py` scripts need an extracted archive and now have no input; the
  `analysis.json`, `placement-summary.json` and `xbatch-summary.json` outputs they produced are
  retained instead.
- The `study-analysis.py` / `analyze-split.py` replays for `quiet50-20260908` and
  `split50-20260908`. Those analysis scripts lived inside the archives. Their `summary.json` files
  retain every three-try timing, per-query and suite statistic, modality screen and pair estimate,
  so the reported numbers stay inspectable; recomputing them from raw logs does not.
- The parked working directory of `thermal-20260908`. Its retained `raw/*.txt` logs, `tries.csv`
  and CSVs stay inspectable, and `scores.json` keeps the per-query hot time and ln contribution,
  suite hot seconds, sum-ln and geometric mean that the study reported. Those exports are no longer
  rankable — they declare the `diagnostic` regime — so `scores.json` is where the figures live.

## What cannot be recaptured at all

The thermal series and its `cool-02` transition run were taken under the pre-cap power regime
(200 W MSR long-term, 45 W MMIO), before the captain applied the sustained 50 W package cap. That
machine state no longer exists. Nothing discarded here can be regenerated by rerunning the rig
today; a new run would measure a different physical regime.

## Disposition: contained only if the merge is a squash, and nothing here enforces that

Removing the files at the branch tip stops future checkouts from materializing them in the working
tree, but the blobs stay reachable from the earlier commits on this branch that added them
(`f7c7f991c`, `9c9c791a3`, `6a244c6d3`). No history was rewritten here, so anyone cloning this
working branch — or fetching the pull request's refs from the remote — still transfers about 40 MB
of archive objects, and will continue to after this branch is pushed.

Firstmate has stated it intends to **squash-merge** this pull request, and Firstmate owns that
merge. If it is squashed, the campaign branch receives a single commit carrying only the final tree
and these blobs never enter its ancestry — exclusion from campaign history, not erasure, since the
working branch, the remote branch ref and the pull request refs can all keep the objects for as long
as they exist and a clone of any of those still pays the download.

This repository does not enforce that intent. There is no merge-strategy policy file and no branch
setting here that restricts the merge method, so the containment depends on Firstmate carrying out
its stated intent at merge time. **If this lands as a merge commit instead, the containment does not
happen**: the three commits above become part of the campaign line's ancestry and it inherits the
~40 MB permanently, which is the outcome this section exists to avoid. Anyone performing the merge
should treat squashing as a requirement, not a preference.
